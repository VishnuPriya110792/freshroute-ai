# FreshRoute AI — outcome tracking

## 1. Operational overview and navigation — complete
- Build the actual working FreshRoute AI dashboard, not a landing page or static mockup; a first-time user can complete the workflow without a tutorial or external API key.
- Use the active dataset and current real backend result to show total available stock (kg), total allocated stock, unallocated stock, estimated demand fulfillment percentage, clearly defined estimated spoilage/at-risk quantity, transport cost, estimated net revenue, and baseline-versus-optimized difference. Give every metric a definition or accessible explanation; before a plan exists, show a helpful empty state rather than invented results.
- Include an inventory shelf-life risk chart, destination demand-versus-allocation chart, concise dispatch-priority table, and visible generate/recalculate action. All chart values come from actual calculations.
- Provide brand, navigation, dataset/scenario indicator, primary action, synthetic-data disclosure, responsive/accessible controls, useful loading/empty/success/error states, keyboard operability and high-contrast legible charts/tables.

## 2. Inventory, destinations, and validation — complete
- Show batch ID, commodity, available quantity, estimated remaining usable shelf life, handling/delivery restrictions, and destination eligibility. Allow loading sample data, CSV upload, inspecting validation errors, editing relevant values, restoring the original sample, and downloading a CSV template.
- Validate types, required columns, quantities, time units, missing values, duplicate IDs and invalid constraints. Never silently discard invalid rows; provide actionable errors.
- Provide destination/transport data view or editor for demand by commodity, selling price/kg, travel time, transport cost, available capacity, and handling time. Document schemas in the README and CSV template.
- Sample data is deterministic, self-contained, internally consistent synthetic Indian produce distribution (including tomatoes, bananas, mangoes, onions and leafy vegetables), with several batches, multiple markets, varying remaining life, demand/prices/travel/cost/capacity, feasible and infeasible options, and illustrative synthetic price/time/shelf-life values that are not official statistics or verified current prices.

## 3. Allocation planner, hard constraints, and explanations — complete
- Implement the allocation engine as a separate documented Python module with clear input/output schema and explicit objective: maximize expected net contribution of feasible deliveries using selling revenue minus transport cost, with no arbitrary unexplained weights.
- Model one dispatch planning horizon and explicitly define capacity interpretation. Enforce inventory ceilings, eligible commodity-destination demand ceilings, modeled route capacity, delivery plus handling within remaining usable shelf life, destination eligibility, nonnegative assignments, valid destination/transport assignment for each allocated unit, and inventory/allocation/rejected/remaining reconciliation.
- Avoid double-counting spoilage, lost sales and revenue penalties. Treat shelf-life values as input estimates, not physical guarantees. Return structured infeasibility status/diagnostics if needed; never fabricate a feasible allocation.
- Show sortable allocations with batch/destination IDs, kg, expected delivery time, estimated usable shelf life on arrival, transport cost, feasibility and a concise input-grounded reason for each decision. Show allocated and unallocated stock, unfulfilled demand, shelf-life rejected stock, capacity limitations and other infeasibility. Every number is backend-calculated and returned to the frontend.

## 4. FEFO baseline and comparable evaluation — complete
- Implement a reproducible earliest-expiry-first baseline: prioritize feasible batches by less remaining usable life; obey the same inventory, demand, shelf-life, eligibility and transport constraints; use the same prices/cost assumptions; never duplicate inventory; account for unallocated stock; document stable tie-breaking.
- Evaluate baseline and optimizer on the exact same inputs with one authoritative evaluation function. Report delivered quantity, demand fulfillment, unallocated quantity, estimated unsold/spoilage under explicit assumptions, gross sales revenue, transport costs, discount-related revenue effects where applicable, other defined operating costs and net revenue after defined costs.
- Define metric formulas and units. Distinguish physically expired, unsold, at-risk and destination-rejected inventory; do not call all unallocated stock spoiled. Show absolute/percentage differences only when denominators are meaningful, identify metrics that improve/worsen, and never force the optimizer to win every metric.
- Include a deterministic evaluation script for normal operations, short remaining shelf life, demand spike, transport delay and reduced vehicle capacity. Report actual outcomes, including any strategy metric that is worse; keep evaluation scenarios separate from tuning where feasible.

## 5. What-if simulator — complete
- Provide bounded controls with visible units to increase/decrease travel time, destination demand and available transport capacity. Running a scenario preserves the original dataset and modifies a separate copy, recomputes baseline and optimized plans, and displays new allocations/metrics, the most significant changes and input-grounded explanations. Reset Scenario restores the original scenario. Controls must change calculation inputs, not merely presentation.

## 6. Discount recommendations and real exports — complete
- Implement deterministic rule-based recommendations for residual batches at risk of remaining unsold or becoming unusable before sale, based on remaining shelf life, unallocated quantity, expected destination demand, delivery feasibility and available selling prices.
- Show recommended discount %, discounted selling price, estimated revenue trade-off and plain-language reason. State that the estimate is rule-based and that no increase in demand is claimed without validated demand-response data.
- Provide functional allocation-results CSV export, baseline-comparison CSV export and a printable summary report with actual inputs/assumptions, recommendations, key metrics, constraints and limitations. Do not serve static/empty reports.

## 7. Backend, frontend integration, automated tests and reliability — complete
- Implement documented FastAPI REST endpoints equivalent to GET `/health`, GET `/api/sample-data`, POST `/api/inventory/validate`, POST `/api/optimize`, POST `/api/compare`, POST `/api/scenarios/simulate` and POST `/api/reports/export` (reasonable naming changes allowed). Use Pydantic request/response models, explicit validation, useful status codes and structured errors, correct CORS if needed, no code secrets, and no mocked core-plan results.
- Frontend calls the real backend for allocation, scenarios and all core metric calculations. Backend failures are understandable and recoverable. App starts with sample data, has stable units, preserves original inputs in simulations, gives calculation/loading feedback, handles bad inputs, and has no paid APIs/live data dependency. Core metric formulas exist only in the authoritative backend evaluator.
- Test real calculations: allocation ≤ inventory; allocation ≤ destination demand; transport capacity; shelf-life; eligibility; reject negative quantities; zero demand → zero allocation; zero route capacity → no transport through that capacity; correct inventory reconciliation; manually checked revenue/transport costs; baseline/optimizer same economic assumptions; scenario affects actual computation; invalid CSV has useful errors; repeated inputs deterministic; infeasible inputs do not crash or create invalid allocations.
- Run tests and frontend build and report only actual results. Calculations must remain interactive for small hackathon datasets on a student laptop.
